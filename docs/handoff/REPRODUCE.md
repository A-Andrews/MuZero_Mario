# Reproduce the handoff

Two verification tiers are separate: a fresh lightweight environment for figures/presentation, and the working GPU/emulator environment for model execution. An environment inventory is not evidence of a fresh installation of the complete training stack.

## 1. Figures and presentation on a clean Python environment

Use **Python 3.11** explicitly. This host's bare `python3` is older and cannot install the pinned plotting packages.

```bash
python3.11 -m venv /tmp/muzero-handoff-figures
/tmp/muzero-handoff-figures/bin/python -m pip install -r docs/handoff/requirements-figures.lock.txt
/tmp/muzero-handoff-figures/bin/python scripts/plot_project_handoff.py
/tmp/muzero-handoff-figures/bin/python scripts/build_handoff_presentation.py
```

Expected: five original figures plus two follow-up figures, each in PNG/PDF/SVG; benchmark CSV and provenance JSON; thirteen-slide HTML/PDF and speaker notes under `docs/handoff/presentation/`. These commands read the portable evidence snapshots. They do not require torch, the ROM, raw human data, model checkpoints or the output mount. Existing video files are preserved, not regenerated by the presentation builder.

The clean environment was installed from the package index using Python 3.11.13 on aarch64. `requirements-figures.lock.txt` captures all resolved packages. This is a version lock, not a multi-platform wheel/hash lock. Another OS/architecture may resolve different binary wheels. The working cluster environment is separately recorded in `verification/environment-packages.txt` and `environment.json`.

## 2. Rebuild the diagnostic evidence from raw summaries

Only necessary when checking provenance or deliberately creating a new dated snapshot. Requires the two completed source summaries and their external directories:

```bash
.venv/bin/python scripts/snapshot_handoff_diagnostics.py
```

Expected: validation of 56 recovered search-leaf roots, 224,000 baseline backups, 2,800 value-target records and 280 root/arm endpoint summaries. This script overwrites the September 20 portable diagnostic snapshot, so preserve it first if using new source data. The earlier performance snapshot remains a frozen source-hashed input rather than a live cohort selection.

## 3. Check a model and render evidence-linked clips on the cluster

From the repository root, using the established cluster `.venv` and project access:

```bash
sbatch scripts/submit_handoff_validation.sh "$PWD/diagnostic_outputs/handoff-validation-local"
```

Resources: one GPU, four CPUs, 16 GB RAM, 20-minute maximum. The successful model-only retry took about 395 seconds inside the Python runner, including checkpoint access/evaluation. Queue wait and shared-filesystem throughput are additional and variable. The initial clip-rendering pass also verified six full recorded trajectories.

The workflow runs 36 focused tests (network, MCTS, stochastic starts and stall controller), verifies checkpoint/trace hashes, replays six existing episodes into labelled MP4 excerpts, and runs one greedy Level6-1 evaluation from the **development** manifest. It writes `tests.txt`, `clips/manifest.json`, `model_smoke/summary.json` and `result.json`.

Expected: `result.json` has `passed=true`, six clips and CUDA available. `model_smoke/summary.json` has `complete=true`, one finished trial and zero infrastructure errors. The tested development episode completed; this is a reproducibility check, not a new success-rate estimate. Do not require every future smoke configuration to win merely to prove that the pipeline runs.

If clips already exist and only inference needs checking:

```bash
sbatch scripts/submit_handoff_validation.sh "$PWD/diagnostic_outputs/handoff-validation-local" --smoke-only
```

Use a new output directory for an independent run. The evaluation runner retains completed records on resume, so reusing `model_smoke/` does not prove inference was repeated.

Validation provenance: initial handoff job 6723040 passed the 36 tests and all six full trace replays, then correctly rejected a confirmation-manifest smoke request. The corrected job 6723098 uses the development manifest and passed the model check. No confirmation trials were added. The guard failure and correction are retained in cluster logs. Selected verification outputs are copied to `verification/`; clip sources and hashes are in the clip manifest.
